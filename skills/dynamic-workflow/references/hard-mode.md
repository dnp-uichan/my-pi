# Hard 실행 지침

`dynamic-workflow` 실행 인자의 첫 토큰이 정확히 `hard`일 때만 로드하고 적용한다. 일반 실행이나 단계 스킬의 공통 참고자료로 선행 로드하지 않는다. 이 파일을 편집·검토하기 위해 읽는 것 자체는 실행 모드를 활성화하지 않는다.

## 적용 범위

- 현재 작업의 개발 흐름에 추가하는 단계 준수 규칙이다. 기본 품질·안전·프로젝트 규칙을 대체하거나 완화하지 않는다.
- 시작할 때 `hard` 선택과 요청한 종료 지점을 밝힌다. 이후 같은 작업의 단계 전환·개선·위임에서는 옵션을 반복 입력받지 않는다.
- 하위 스킬에 기본 비적용 판단이 허용돼 있어도 이 파일의 추가 승인 조건을 함께 적용한다. 위임 시 작업 범위와 함께 이 제약을 전달한다.
- 새 작업에는 자동 상속하지 않는다. 조사·설명·단계 단독 요청을 임의로 전체 개발 작업으로 확대하지 않는다.
- 적용은 에이전트 지침 수준이다. hook·extension으로 도구를 차단하거나 이미 읽은 내용을 컨텍스트에서 제거하는 기능이 있다고 주장하지 않는다.

## 단계 순서와 예외

준비에서 요구사항·변경 계획·테스트 계획을 확인한 뒤 요청한 종료 지점까지 진행한다.

`테스트 작성 → 구현 → 정적 분석 → 독립 검수 → 필요한 개선·재검증 → commit → PR`

- 메인과 서브에이전트는 단계 순서·적용 여부를 임의로 바꾸지 않는다.
- 테스트 작성이나 정적 분석 등이 불필요해 보여도 단계 비적용·대체·생략이 필요하면 이유와 대체 검증을 설명하고 사용자 확인을 받는다. 문서만 바꾸는 작업도 동일하다.
- 사용자가 해당 작업에 이미 승인한 예외는 기록하고 다시 묻지 않는다. 필수 안전·프로젝트 규칙을 예외 승인으로 우회하지 않는다.
- 개선할 문제가 없음을 독립 검수로 확인했다면 개선 단계 통과다. 불필요한 변경이나 실패 테스트를 억지로 만들지 않는다.

## 단계별 증거

- 대상 파일/revision 또는 작업 상태와 실행 명령·범위·실제 결과를 연결한다. 각 단계의 통과 근거를 확인하기 전에 다음 단계로 진행하지 않는다.
- 테스트 작성에서는 의도한 동작 assertion 실패인 Red, 기존 동작 회귀 테스트의 통과, 구현 미존재로 인한 실행 불가를 구분한다.
- 구현 파일·공개 인터페이스 미존재로 실행하지 못한 항목은 원인을 기록해 구현으로 인계하고, 구현 후 실제 동작 검증을 반드시 확인한다. 러너·설정·의존성 등 환경 오류는 Red 통과가 아니라 blocker다.
- 테스트 실패를 발견하면 즉시 테스트명·원인 추정·다음 조치를 보고한다. 확정된 테스트를 통과시키려고 수정·삭제·약화하지 않는다.
- 검수 후 코드·설정·의존성·계약이 바뀌면 수정 전 증거만으로 완료하지 않는다. 관련 테스트·정적 분석과 독립적인 지적 해결 확인을 갱신한다.
- 적용 가능한 필수 검사·hook은 유지한다. 필요한 실행이 실패하거나 불가능하면 통과·비적용으로 바꾸지 않는다.

## 중단과 권한

- 미해결 blocker, 실행 실패, 시간·예산·반복 한도 도달은 완료가 아니라 중단 사유다. 남은 항목과 필요한 결정을 보고한다.
- `hard`는 종료 지점이나 실행 권한을 추가하지 않는다. 별도 요청이 없으면 개선·재검증까지 진행하며 commit·push·PR·외부 전송은 수행하지 않는다.
- `PR까지`처럼 명시한 권한은 단계마다 재승인받지 않는다. `push 금지` 등 더 좁은 제한은 유지하며 merge·배포로 확장하지 않는다.
